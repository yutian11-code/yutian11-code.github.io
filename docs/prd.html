1. 看穿引擎 ⭐⭐（命门）

做什么：输入一张自拍，调多模态视觉模型，输出一份结构化"洞察结果"。不打分、不做诊断，靠话术工程制造"被看穿感"。

⚠️ 下面 1.1-1.6 的字段名、JSON 结构、system prompt 细节都是参考草案，跟着 §1.2 人设标签库一样待正式设计，不用今晚就抠死具体字段——开发先按这个大致结构跑通联调即可，字段增减、命名后面都可以改。真正不用等、今晚要落实的是 §8 数据埋点里的事件列表，这个不受内容设计影响，可以直接按那张表埋。

1.1 输出数据结构（参考草案，不用抠细节）

{
  "face_features": {
    "face_shape": "enum: 圆脸/方脸/长脸/心形脸/鹅蛋脸",
    "eye_shape": "string", "brow_style": "string", "lip_style": "string",
    "skin_tone_tier": "enum: 白皙/中等/健康小麦/深",
    "expression_vibe": "string", "style_read": "string"
  },
  "persona_tag": "enum，见 1.2",
  "anchor_line": "外貌锚点一句话，必须引用图中可验证细节",
  "first_impression": "第一印象文案，80-120字",
  "contrast_insight": { "misconception": "大家对你的第一印象", "reality": "但实际上……" },
  "quote": "金句，第二人称，15-25字，可独立截图",
  "makeup_direction": "落位一行妆容方向",
  "rarity_pct": "非模型输出，后端计算注入，见 1.4"
}

face_features 是内部字段，不直接展示给用户，只用来生成 anchor_line/makeup_direction 和后续统计。

1.2 人设标签库 ⚠️ 待设计（下表是占位草案，非最终版）

以下 8 个标签、定义关键词、专属色卡直接继承自《妆签 MVP》的经验列表，没有经过针对本产品的重新设计和验证，先当占位草案给今晚开发用（数量 8 个不变，见前面讨论），但具体标签内容、定义关键词、色卡搭配都待正式设计，不代表已经拍板：

人设标签（占位） 定义关键词（占位） 专属色卡（占位）
清冷氛围挂 疏离感、高级感 雾霾蓝、豆沙灰
甜辣御姐挂 攻气、反差萌 正红、酒红
纯欲挂 无辜感、软糯 蜜桃粉、珊瑚橘
复古港风挂 浓颜、精致 大地棕、复古红
元气少女挂 活力、亲和 蜜柑橙、樱花粉
欧美高级挂 立体、大气 焦糖色、深咖
温柔氧气挂 治愈、柔和 燕麦色、奶茶色
酷飒中性挂 利落、少攻击性锋芒 藕荷紫、雾灰蓝

开发先按这份草案接口（enum 8 个值 + 对应色卡）联调，枚举值本身用字符串常量、别写死在业务逻辑里，方便后面正式设计定稿后直接替换值，不用改代码结构。正式设计怎么定，见 §1.7 的两条路径讨论。

1.3 System Prompt 约束（PM 提供初版，需要真机测试迭代）

  • 正向措辞、非诊断、不打分（不允许出现"X 分"这种表述）
  • persona_tag 必须从上表 8 个枚举里选一个，不能自造
  • anchor_line 必须包含至少一个可从照片验证的具体细节词（如"眼尾上扬""下颌线利落"），不能空泛
  • contrast_insight 走"误解框架"：misconception 写外在气质刻板印象，reality 转折到细节反差，语气必须是惊喜发现，不能是否定/冒犯——这条不需要用户输入任何自评信息，全部由模型从照片判断给出
  • quote 第二人称、15-25 字、可独立截图
  • 禁用词表：算命/命运/运势/宜忌/占卜/面相（命理类）；丑/差/缺陷（负面类）；诊断/疾病/治疗（医疗类）；X 分/打分（评分类）

1.4 稀缺感计算（rarity_pct）

后端维护各 persona_tag 历史命中计数，取"占比较小的一侧"展示；若某标签命中率超过 50%，展示口径改为"仅 X% 是高频型"。首炮直接用简单的定时批处理（比如每小时跑一次统计）就行，不需要实时。

1.5 异常与兜底（这条是底线，必须实现）

场景 处理
模型调用超时 重试 1 次 → 仍失败走「保底人设」：按 face_features 粗特征弱匹配最接近标签，套用预置默认文案出卡
返回不符合上面的 JSON 结构 重新请求 1 次 → 仍失败走保底人设
persona_tag 不在 8 个枚举内 模型另返回一个"最接近的既有风格"辅助字段，后端做映射；映射不到走保底人设
命中禁用词 重新生成 1 次 → 仍命中则替换成预置安全文案

原则：宁可不个性化，也不能不出卡。这条是产品能不能用的底线，务必优先测试这个分支。

1.6 待确认（今天先给个默认值，别卡在这里）

  • 模型选型 + 响应时间：先选定一个可用的多模态模型跑通，目标响应时间先按 ≤8 秒设计等待态，后面根据实测再调
  • 这块建议先跑通再优化话术准度，准度校准是持续迭代的事，不阻塞今晚的联调

1.7 人设标签背后的判断维度（不阻塞今晚，先记录设计思路，后续验证）

现在的设计是：§1.1 提取 7 个原始视觉维度（脸型/眼型/眉形/唇形/肤色档/神态/穿搭风格）后，由模型整体判断直接给出 1 个 persona_tag，中间没有一套显式的"维度组合公式"——不像 MBTI 是 4 个独立二元维度严格组合出 16 型（2⁴）。这是自拍版的有意选择：整体判断更贴近"AI 在看你"的巴纳姆式体验，而不是"套公式算你"。

如果想让判断更一致、可复现，可以补一套显式维度规则，思路是找 3 个正交二元轴，2³=8 刚好对应现在的 8 个标签：

  • 温度感：冷 / 暖
  • 浓淡感：浓郁强势 / 清淡内敛
  • 软硬度：锐利 / 柔和

⚠️ 如实说明一个问题：现有这 8 个标签是从《妆签 MVP》直接继承的经验列表，不是从这 3 个轴推导出来的，尝试往回套的时候有明显冲突——比如"元气少女挂"和"温柔氧气挂"用这套轴去分都落在"暖+柔"附近，区分度不够；"复古港风挂"和"甜辣御姐挂"也有类似重叠。也就是说，这 8 个标签目前不是一套干净的正交维度体系，勉强拿三轴去套会产生歧义，不能直接拿来当查表规则用。

两条后续路径（哪条都不用今晚做）： 1. 轻量方案：把"温度感/浓淡感/软硬度"这 3 条只当成 system prompt 里给模型的判断辅助提示（"依次考虑温度感、浓淡感、软硬度，再从 8 个标签里选最接近的"），不做成硬编码查表，能提升一些一致性，但不解决标签本身有重叠的问题。 2. 重设计方案：以后如果真要做成 MBTI 那种严格的"维度组合"体系，需要重新设计这 8 个标签本身，让它们对齐到干净的正交轴上（而不是现在这样反向拿轴去套一份已经写好的经验列表），这是内容侧的一次改版，工作量不小，放 V1.1 评估要不要做。

2. 身份卡渲染 ⭐⭐（命门，传播单元）

做什么：把 §1 的输出渲染成一张可截图分享的卡片（小程序 Canvas）。

信息层级（从上到下）：

层级 内容
1 人设标签大字（如"清冷氛围挂"）—— 最大字号
2 金句 —— 独立区域，方便只截这一句
3 外貌锚点一句话
4 反差洞察（误解 + 反差两句）
5 妆容方向一行
6 稀缺感标注（"只有 X% 是清冷氛围挂"）
7 底部分享区 + 小程序码

示例（直接照这个做视觉稿）：

清冷氛围挂 ·「你安静的时候，气场比说话时更响。」 锚点：眼尾微微上扬，笑起来才露出一点软。 反差：大家对你的第一印象是很飒很难接近，但你笑起来时眼睛会先弯——这种反差感很戳人。 妆容方向：淡雾感底妆 + 豆沙灰眼影，别加太多暖调。 只有 17% 的人被判定为清冷氛围挂。

技术要求：Canvas 渲染，主流 iOS/Android 微信客户端真机测试保存图/截图不错位、不截断（这条必须测，卡片是唯一的传播载体）。

卡片可点开详情页（原型 A7）：结果页的简版卡整卡可点击，展开"完整解读"详情页——first_impression（80-120 字第一印象全文）只在详情页展示，简版卡不放（保持一屏可截图的克制）。详情页同样挂分享三件套。分层逻辑：简版卡 = 传播用，详情页 = 价值兑现。埋点 card_detail_view。

3. 自拍上传 + 前置校验 ⭐

在"选照片"这一步之前，先过 §7 的使用次数门槛检查（第 1 次直接放行，第 2 次起需要解锁）。

步骤 交互
选照片 微信原生 chooseMedia（拍照/相册二选一）
预览确认 本地预览 +「确认，开始看穿」/「重新选择」
前置校验 见下表
校验结果 提示文案 阻断力度
无人脸 "没看清你的脸呀，换张露脸的照片试试～" 硬性阻断，必须重传
多人脸 "这张照片不止一张脸，选一张只有你自己的吧～" 硬性阻断，必须重传
过暗/过糊 "这张照片有点暗/模糊，可能影响看穿效果，要不要换一张？" 软提示，给【重传】【仍然继续】两个按钮
通过 — 直接进入等待态

过暗/过糊的判定算法由开发自行选型（简单的亮度/清晰度检测即可，不需要额外调模型），阈值先给个粗略值，上线后再调。

4. 落地引导页 + 全局导航「我的」

4.1 落地引导页 - 首屏：1-2 张样例卡（先拿 §2 的示例卡片当素材）+「上传自拍」大按钮 + 底部一句隐私说明（"你的照片仅用于本次生成，用完即焚，不会被保存"，点击展开完整条款） - 从互测邀请链接进来的用户不经过这个页面，直接进 §6 的投票页

4.2 底部 tabBar + 「我的」页（原型 D1） - tabBar 两个 tab：看穿（落地引导页）/ 我的。仅 tab 页显示，流程中间页（上传/等待/结果）无 tabBar（小程序原生行为）。 - 「我的」页是轻量版，只放三样东西： 1. 我的风格卡（仅最近一张，重测覆盖）→ 点开进 §2 的详情页 2. 我的互测入口（"5 位朋友已投 · 查看"）→ 进互测结果页。这就是拒绝推送授权用户的手动回访路径，解决了之前遗留的开放问题 3. 再测一次按钮（第 2 次起走 §7 解锁门槛） - 空态：没测过 → "还没有风格卡，去测一张"引导去落地页 - 边界（防蔓延）：无收藏、无历史列表、无档案沉淀——那些是 V1.1「我的形象档案」的事，这里只是"最近一张卡 + 互测回访"的最小入口，开发不要做重。 - 埋点 my_page_view。

6. 闺蜜互测「别人眼里的你」⭐（工程量最大的一块，两个开发建议一人主看穿引擎、一人主这块）

边界：不做"是谁投的"、不做互测历史列表、不做付费解锁。只做"发起 → 匿名投票 → 回访看汇总结果 + 一条推送"。

📌 待细化的页面结构原则（先记下结论，具体视觉/交互回头再设计）：F 打开互测卡后，"测试你自己"和"猜猜 TA 的风格"两个入口同屏并存，不是强制先后顺序；"测试你自己"是主入口、视觉更显眼，"猜猜 TA"是次入口、更小。这条结构性要求已经反映进下面的时序图，具体页面怎么摆（按钮大小/位置/文案）留到详细页面设计时再定。

6.2 数据结构

互测任务表：duel_id / initiator_openid / initiator_persona_tag（仅结果页对比用，不对朋友展示）/ created_at / pushed_milestones（已推送过的里程碑列表，如 [1]、[1,5]，保证同一里程碑只推1次）

投票记录表：duel_id / voter_openid（仅去重，不展示）/ voted_persona_tag / voted_at，唯一约束 (duel_id, voter_openid)（防重复投票）

无需复杂状态机——互测任务发起后即可持续接受投票、持续被查看，没有"锁定/解锁/过期"这些状态流转，pushed_milestones 只是记录"1 票、5 票这两个里程碑分别有没有推送过"的简单标记，新增投票时检查当前票数是否命中未推送过的里程碑（[1, 5]），命中则推送并记录。

6.3 关键规则

  • 互测卡不展示发起者自己的 AI 判定结果（否则朋友"猜"没意义）
  • 投票无需登录，openid 静默识别，同一 openid 对同一互测限投 1 次
  • 结果页永远可查看、实时更新，展示当前汇总投票分布（走"排行榜"风格，不是"最终报告"风格，1 票也直接展示）+ 与 AI 结果对比（比如"AI 说你是清冷挂，朋友也这么觉得"），不展示任何投票者身份
  • 推送按里程碑触发（第 1 票、第 5 票各推 1 次，封顶 2 次），作为"有人来猜你了/更多人来猜了"的提醒，跟"能不能看结果"无关（结果随时能看，不依赖推送）
  • 同一时间只允许一个"进行中"的互测，重新发起覆盖上一个未完成的（简化状态管理）
  • 不允许为了避免结果冷清而人工刷票/编造虚假投票——NGL/Sendit 就因编造虚假消息诱导付费解锁被美国监管处罚，这条红线不能碰

6.4 朋友投票后，怎么更好地转化他去测试自己

投票完只甩一句通用的"你也来测测"太弱，转化率不会高。改成利用他刚才的猜测本身当钩子：

  • 引导文案不再是通用的，而是引用他刚投的那个标签："你猜 TA 是清冷氛围挂——你自己是不是也是这一挂？测测看"
  • "先猜后测"反差钩子（核心改动）：F 测完自己之后，结果页额外插一句对比："你猜 TA 是清冷氛围挂，你自己测出来是甜辣御姐挂——你俩完全不是一类人"（或"你俩撞挂了，怪不得这么合得来"）。不管猜没猜中都有内容可讲，这是比"猜没猜中"更有意思的二次爽点，也是让 F 愿意测完自己的直接动机。
  • 降低点击到测试的摩擦：F 是从互测卡进来的，已经对这个产品有认知了，点击"测测你自己"应该直接跳进上传页，不用再看一遍落地页的介绍样例卡（那套是给冷启动流量看的，F 不需要）。
  • 这个转化本身需要落到具体页面参数上：F 的自拍上传流程要带上来源标记（referral_duel_id + 当时猜的 guessed_persona_tag），这样 F 出卡后才能生成上面那句"先猜后测"对比文案，也才能在埋点里算出完整转化率（见 §8）。

6.5 发起者的持续闭环（避免"分享一次就用完"）

分享出去之后，发起者只有"等推送"这一个理由回来，确实太单薄，加两个低成本的东西：

  • 结果页生成"对比卡"再分享 ⭐：把当前投票汇总也做成一张可截图卡片（"朋友们都觉得我是XX挂" + AI 自己的判定结果对比），走跟 §2 身份卡一样的分享三件套（存图/海报/转发）。这样"看结果"这个动作本身又生产出一张新的传播物料，形成"分享→收票→生成对比卡→再分享"的小闭环，而不是分享一次就断了。
  • 推送改成"里程碑式"，不是只推 1 次：第 1 票推送 1 次；之后再新增到一个里程碑（比如第 5 票）再推 1 次，总共 2-3 次封顶，不做成无限推送骚扰，但也别完全静默——只推 1 次的话大概率用户看完就再也不会主动想起回来看了。
  • 结果页留一个"再来一轮·换一批朋友测测"入口：允许发起者对同一个人设卡重新发起一轮互测（比如测完闺蜜群还想拿去问同事群），让互测本身可以被重复触发，而不是一次性用完的工具。

这几条不是"加留存深度"（那类东西仍然按定稿后置到 V1.1），而是让互测本身（首炮里已经决定要做的裂变+留存双引擎）真正起到该起的作用——如果分享一次就死，互测回访率这个核心指标从设计上就跑不出来。

7. 使用次数限制与变现门槛 ⭐（新增）

规则：每个用户（按 openid 计，仅统计成功出卡次数）——

第几次 门槛
第 1 次 完全免费，无门槛
第 2 次 看完 1 次激励视频广告即可解锁
第 3 次及以后 二选一：看视频解锁 / 付费解锁

⚠️ 明确不做"拉好友解锁"：原方案里"拉好友才能解锁使用次数"已经排除——这跟 §6 互测里"转发给朋友"性质完全不同：互测的分享是用户自愿发起、不解锁任何东西（不分享也能正常用自己的功能），而"拉好友才能继续用"是把继续使用的权限跟邀请行为强制绑定，正好命中《微信外部链接内容管理规范》2.1.2 条"邀请好友协助"的禁止范围（见 §6.1 上方的设计变更说明）。"拉好友"这件事只应该自然存在于互测这个功能本身里，不应该被用作次数限制的解锁手段，两者不能混为一谈。

交互流程：用户点击「上传自拍」发起新一次测试 → 后端查该 openid 的历史成功出卡次数 → 命中第 2 次或以上的门槛 → 弹出解锁选择（第2次只显示"看视频"；第3次起同时显示"看视频"/"付费"两个按钮）→ 解锁成功才放行进入 §3 的上传流程；中途关闭广告/取消支付则不放行，可重新触发。

技术依赖（这两项申请/接入都有审核周期，比开发本身更容易卡上线时间，今天就要去启动）： - 微信小程序流量主-激励视频广告开通与广告位申请 - 微信支付商户号接入（若还没有）

待拍板：付费解锁的具体定价（单次价格，今天先给个默认值，比如 ¥3-6，别为这个卡进度，后面随时能改）。

男性用户上传自拍怎么处理——已有建议，不用再纠结：

不做性别检测，男性和女性走完全同一套逻辑（同样 8 个人设标签 + 妆容方向），不新增任何判断分支。理由： - 首炮赌的是传播，不是精准服务某一群体。男性测出"甜辣御姐挂"配一句妆容建议，大概率不是体验事故，反而可能因为反差/好笑而更愿意截图分享——这本身是一种社交货币，跟测试类产品"梗"的传播逻辑是一致的（不是bug，是feature）。 - 做性别检测反而增加成本和风险：多一次判断逻辑、模型判断性别本身可能出错、"根据外貌判断性别再区别对待"这件事本身也有冒犯争议——不做才是更安全、更省事的选择。 - 唯一的违和点只在"妆容方向"这一行文案，不影响人设标签/金句/反差洞察这些核心体验。上线后如果真实数据显示男性用户占比高、且流失/差评明显，再考虑把"妆容方向"换成更中性的"风格方向"表述（内容侧小改，不影响引擎结构），不需要现在就设计。
